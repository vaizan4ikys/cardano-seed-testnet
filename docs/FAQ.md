# FAQ: questions a leader or reviewer will ask

All numbers come from the files named in each answer. Everything was measured on a **private test chain** (3 pools, about 5 s per block, simulated sensors), not on Cardano mainnet. Where two sources disagree, the answer says so.

Short names: [`PHASE0`](../experiments/contract/PHASE0-NOTES.md), [`PHASE3`](../experiments/contract/PHASE3-RESULTS.md), [`report`](measurement-report.html), [`demo README`](../experiments/demo/README.md), [`pipeline README`](../experiments/pipeline/README.md), [`spec README`](../spec/README.md).

## 1. Why Cardano instead of Ethereum here?

The project README says only that Cardano replaces Ethereum as the ledger ([`README.md`](../README.md)); the report says the same for the earlier SEED project (report, "What was built"). This repo has no side-by-side test of the two, so it cannot say that Cardano is better. What the repo does show about Cardano: a transaction can carry sensor data as metadata (up to 16,384 bytes per transaction, [`spec README`](../spec/README.md)); the fee follows a fixed formula, so it can be computed before sending (`1 * size + 0.0577 * memory + 0.0000721 * steps` on the test chain, [`PHASE0`](../experiments/contract/PHASE0-NOTES.md), task 1); and the node itself refuses a transaction whose smart contract fails, before it reaches the waiting room, so no collateral is taken ([`PHASE0`](../experiments/contract/PHASE0-NOTES.md), task 1).

## 2. What exactly does the smart contract guarantee, and what does it not?

**It guarantees:** a data transaction can mint its receipt token only if the registry coin is attached and at least one signer of the transaction is on the registry list. Gateway B (not on the list) was refused by the node at submit; gateway A was accepted ([`PHASE0`](../experiments/contract/PHASE0-NOTES.md), task 1). Only one registry coin can ever exist, because the registry token is minted by a one-shot policy; a look-alike coin with another policy is ignored ([`PHASE0`](../experiments/contract/PHASE0-NOTES.md), guards G1 and G2). The page shows only transactions that carry a receipt.

**It does not guarantee:**

* **Good data from an enrolled gateway.** The contract cannot read the metadata. It only gets the 32-byte batch hash as redeemer, and the page checks the hash off-chain (`gateway_write.ak`, comment at the top). An approved gateway can write junk, and nothing on the chain says it is junk. The sensors themselves are simulated and are not authenticated ([`demo README`](../experiments/demo/README.md), Limits).
* **Protection against a stolen gateway key.** Identity is the signer address; there is no IP or device identity ([`demo README`](../experiments/demo/README.md), Limits). Whoever holds an enrolled key can write until the administrator revokes it.
* **Protection against the administrator key.** It sits in the pool-1 container (`/tmp/p0n/admin.skey`). Anyone with docker access on that machine can enrol or revoke any gateway; one key, no second signature, no delay ([`demo README`](../experiments/demo/README.md), Limits).
* **That nobody else writes.** Any wallet on this chain can send a transaction with junk metadata and no receipt; the page ignores it. Unless the page server runs with `--receipt-policy <policy id>`, a receipt of any policy counts, and the demo does not set it ([`demo README`](../experiments/demo/README.md), Limits).
* **Retroactive revocation.** Batches already in a block stay ([`demo README`](../experiments/demo/README.md), Limits).

## 3. How fast is data final, and what does "final" mean?

A transaction is in a block after about 6 s (6.1 s on average). It is "final" after 60 more blocks, which took about 310 s, a little over 5 minutes (295 to 332 s over 12 transactions) (report, section 8). "Final" here means: more than k = 60 blocks deep, so it can no longer be rolled back on this chain ([`spec README`](../spec/README.md): `securityParam` 60). Before that the page shows "Settling n / 60". This is the security of a private chain with 3 pools, not of a public chain ([`demo README`](../experiments/demo/README.md), Limits). The mainnet-like parameter set in the repo uses k = 2160 with one block per 20 s ([`spec README`](../spec/README.md)); the repo does not measure finality for it.

## 4. How much data per transaction and per second can the chain take?

* **Per transaction:** at most 16,384 bytes. One reading costs about 8 to 9 bytes in our layout, so a contract transaction takes up to 1,859 readings with 10 sensors in the batch (reserve 1,500 bytes) ([`pipeline README`](../experiments/pipeline/README.md), size section). The demo uses batches of 100 readings.
* **Per block:** the block limit is 65,536 bytes. With the contract and 100 readings per batch a block holds 28 batches (64,064 bytes in all 6 repetitions); with the reference-script variant 39 ([`PHASE3`](../experiments/contract/PHASE3-RESULTS.md), Part B).
* **Per second:** at 6.7 batches per second offered (about 670 readings per second) the contract variant delivered 489 readings per second (median), with median latency 11.8 s; a plain metadata transaction delivered 630 ([`PHASE3`](../experiments/contract/PHASE3-RESULTS.md), Part B).

The report gives a lower figure: about 280 readings per second with 100 readings per transaction, and 100 to 120 with 20-second blocks (report, section 6). The two do not conflict. In the report each reading is a 40-character text, so a 100-reading transaction is 4,444 bytes; in the pipeline layout it is about 1.3 KB without the contract. Smaller readings mean more per block. Both are test-network values: 5 s blocks, one VM with shared CPUs. Do not read them as mainnet capacity ([`PHASE3`](../experiments/contract/PHASE3-RESULTS.md), "What this does not show"). Keep the load under about 70 % of the limit, because the waiting time jumps from seconds to minutes at the limit (report, section 6).

## 5. What does it cost?

On the test chain the fee is 1 lovelace per byte, no fixed part. One batch of 100 readings: 2,263 lovelace without the contract (1,264 bytes); with the contract 10,536 lovelace with 3 keys on the list, 13,835 with 10 keys and 32,682 with 50 keys (2,289 bytes, margin of 1,000 lovelace included). Every key on the list adds script steps, about 1.6 M per key ([`PHASE3`](../experiments/contract/PHASE3-RESULTS.md), Part A).

**These are not mainnet fees.** [`PHASE3`](../experiments/contract/PHASE3-RESULTS.md) notes that mainnet charges 44 lovelace per byte plus a fixed part, and for reference scripts too. The report calculates (from the fee formula, no measurement, no script costs, no ADA price) 0.351 ADA for a 4,444-byte transaction of 100 readings, about 30,000 ADA per day at 100 readings per second, and about 240 ADA per day if only a hash of each minute is stored (report, section 6). That calculation uses the larger 40-character readings, so it is not the cost of the demo layout.

## 6. What happens if a gateway or a site loses its network?

The gateway keeps every batch as a file in its outbox and tries again. With the default settings (`--retry 10`: one try per 10 s, `--max-tries 5`) a batch that failed 5 times goes to `dead/` and is not tried again: **its readings are not on the chain** ([`gateway.py`](../experiments/pipeline/gateway.py), `_dead_letter`; options at the end of the file). The patient setting is `--max-tries 1000`; it is used for the site gateways with `MAXTRIES=1000 ./multisite.sh gwrestart K`, and the script comment says "no dead letters for network trouble" ([`multisite.sh`](../experiments/multisite/multisite.sh)). After a restart every batch that is not "sent" is submitted again with the same hash ([`gateway.py`](../experiments/pipeline/gateway.py), docstring). Readings still waiting in memory for their batch are lost if the process is killed hard.

**Measured** (13 November 2026, one site cut off the network for 5 minutes): with the default setting 15 batches (about 1,500 readings) were lost; with `--max-tries 1000` nothing was lost and the 30 waiting batches were on the chain, in order, 5.5 minutes after the reconnect ([`multisite RESULTS`](../experiments/multisite/RESULTS.md), test 4). For the node itself (not the gateway) the report measured catch-up after a cut: 27 to 33 s after 1 minute, 10 to 143 s after 5 minutes, 71 to 87 s after 15 minutes (report, section 8).

## 7. What happens if the chain host stops for more than about 15 minutes?

The chain is dead and cannot be repaired. Blocks are tied to the wall clock; if all nodes stand still for more than 3k/f = 900 s, they cannot continue ([`spec README`](../spec/README.md), [`troubleshooting.md`](troubleshooting.md)). This happens when the VM is shut down, suspended or saved, or the PC sleeps. Make a new chain with `./experiments/demo/fresh.sh --yes`; the old demo data is gone ([`INSTALL.md`](INSTALL.md), "Stopping, restarting"). INSTALL.md tells you to do this already after about 10 minutes, to be safe. With the mainnet-like parameters the limit is 36 h ([`spec README`](../spec/README.md)). A single pool that is cut off for 15 minutes cannot rejoin by itself; wiping its database and restarting fixed it in under a minute (report, section 8).

## 8. How do we add or remove a gateway?

The administrator does it in the pool-1 container: `p1-enroll.sh <magic> <name>` and `p1-revoke.sh <magic> <name>` ([`experiments/contract/in-container/`](../experiments/contract/in-container/), commands in [`demo README`](../experiments/demo/README.md), Reset). They spend only the registry coin and make a new one with the new list; the fee is 248 lovelace for a revoke and 281 for an enrol ([`PHASE0`](../experiments/contract/PHASE0-NOTES.md), task 3). Both scripts can be run again without harm. A revoke is in a block after 1 to 11 s there (5.5 s in the demo rehearsal). A transaction prepared before the revoke is refused at submit, except one submitted in the same second, which may get into the same block ([`PHASE0`](../experiments/contract/PHASE0-NOTES.md), task 3). A new gateway needs its own key (made inside its own container), its key hash given to the administrator, and an entry in `experiments/pipeline/gateways.json` so the page can show its name ([`multisite.sh`](../experiments/multisite/multisite.sh), `setup`). Keep the list short: every key costs script steps in every transaction ([`PHASE3`](../experiments/contract/PHASE3-RESULTS.md)).

## 9. Can a stranger read the data?

Yes, in principle. The batch is plain metadata in the transaction (sensor id, kind, value, sequence number; layout in the [`pipeline README`](../experiments/pipeline/README.md)). The repo does not encrypt it. Anyone who can run a node on this chain can read all of it. On this private chain a node needs the genesis files, the same magic number and a pool that accepts its connection. The magic number is only a filter, not a password: a node with the same magic and a different genesis connected but was rejected at the first block; a node with a different magic was refused within 20 ms (report, section 11). A node with the real genesis and the real magic is an ordinary joiner (report, section 11), so network access to a pool is what protects the data. Starting the chain with `EXPOSE=1` makes pool 1 reachable from other machines ([`README.md`](../README.md)); `fresh.sh` starts the chain with `EXPOSE=0` in local mode (the Ubuntu VM case) and `EXPOSE=1` in the Mac-to-`seedvm` mode ([`fresh.sh`](../experiments/demo/fresh.sh), the line that sets `RUNENV`; `EXPOSE=1 ./experiments/demo/fresh.sh --yes` exposes it on your own VM too). The web page listens on `127.0.0.1` only, with no login and no TLS ([`pipeline README`](../experiments/pipeline/README.md)). On a public Cardano chain the same data would be readable by everybody.

## 10. What is NOT done yet?

* **Real sensors.** All sensors are simulated and send TCP lines instead of MQTT ([`demo README`](../experiments/demo/README.md), Limits).
* **Automatic monitoring.** The repo has no monitoring or alerting service. The only alarm is the "Silent" flag on the page, based on the server clock. The report only recommends an alarm when a pool's tip differs from the others (report, "What we would do with it").
* **Mainnet.** Everything runs on a private chain with 3 pools on one VM; fees, block time and k differ from mainnet. The mainnet-like parameter set was used only for fork, join and capacity tests (report).
* **Security audit.** None. [`PHASE0`](../experiments/contract/PHASE0-NOTES.md), "Not verified / still open", lists: protocol version 10 and later not tested, order of transactions inside a block only inferred, and the `publish` handler lets anyone register or delegate the credential.
* **Other gaps:** the demo has not been run end to end on an amd64 Windows PC with VirtualBox ([`INSTALL.md`](INSTALL.md), "Tested on"); the report's measurements come from VMs on one Mac, many from 1 to 3 runs (report, "Read this first"); the cause of the contract's higher script cost with a reference script was not investigated ([`PHASE3`](../experiments/contract/PHASE3-RESULTS.md)).

## 11. Why can a transaction disappear after it was in a block?

Because the block it was in can be dropped. This is a normal part of Cardano, not a bug, and it happens on mainnet too. Two pools can win the same slot (the lottery is drawn for every pool separately), or a pool forges before the block of another pool has reached it. Both forge a block, and every node keeps only one of the two: when the blocks have the same length, the tie-break on the VRF value decides. A node that had its own block first switches to the other one ("Switched to a fork" in the node log) and drops its own block. Cardano does not put the transactions of a dropped block back into the waiting room, so a transaction that had only reached that one pool is gone until somebody sends it again.

**What we measured** (`./scripts/fork-stats.sh` on the test VM, node logs of the 3 pools from 21:34 to 23:00 UTC on 19 November 2026, 85 minutes): the pools forged 1,008 blocks, 949 are in the chain and 59 (5.9 %) are not (pool 1: 24, pool 2: 17, pool 3: 18). All 59 lost a tie against a block in the same slot. The deepest rollback seen was 1 block. One of these dropped blocks (slot 65, 21:35:20) carried a registry transaction that had been sent to pool 1 three seconds earlier; pool 3 had forged the winning block 13 ms before. `./scripts/fork-stats.sh --list` prints every lost block with its time.

**Mainnet.** The same thing happens there, but more rarely: a block comes about every 20 s there (`activeSlotsCoeff` 0.05) and about every 5 s on our test chain (0.2) ([`spec README`](../spec/README.md)). The chance that two pools win the same slot grows with this value, so by our own estimate (not measured) it is about 3 times lower per block on mainnet (about 2.5 % of the blocks there, about 7 % expected here with 3 equal pools; we measured 5.9 %). Ties caused by slow block transfer between far-away pools come on top. We did not measure mainnet.

**What follows from this:**

* The newest block or two can still be replaced. Only a block with 60 more blocks on top is "Final" ([question 3](#3-how-fast-is-data-final-and-what-does-final-mean)); that is why the page shows "Settling n / 60" and why our scripts wait for it.
* Our scripts do not trust "it was in a block": while they wait they send the same transaction again every 10 s; the registry changes, the registry mint and the funding transactions also wait for one more block on top; and the gateway keeps every batch until it is final (60 blocks) and sends it again if it is gone from the chain.
* Sending the same signed transaction again is safe. It has one fixed transaction ID and spends fixed inputs, so it can be in the chain only once: a node that already has it in a block, or whose inputs are already spent, rejects the second copy and nothing is paid twice.
